# Person 2 — Matching & ML Module Documentation

## 1. Executive Summary & Architecture

The **Matching / ML Module** (`src/matching/`) forms the downstream scoring and decisioning layer of the entity resolution pipeline. It consumes candidate pairs generated by the upstream candidate generation / blocking stage (Person 3), extracts a 25-dimensional vector of pairwise similarities using the normalization standards established by Person 1, predicts calibrated match probabilities using a regularized classifier, and applies a macro $F_{0.5}$-optimized decision threshold to produce the final competition submission.

```
Candidate Pairs (Person 3)
         │
         ▼
┌────────────────────────────────────────────────────────┐
│ Pairwise Feature Extraction (features.py)              │
│  • Name similarities (Jaccard, Levenshtein, Dice, etc.)│
│  • Address similarities (Jaccard, Levenshtein, n-gram) │
│  • Numeric agreement / disagreement (strongest signal) │
│  • Open-set country comparison (US, India, France)     │
│  • Missing value indicators                            │
└──────────────────────────┬─────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│ Grouped Supervised Training & Validation (train.py)    │
│  • GroupShuffleSplit (group = source1_entity_id)       │
│  • 0% Entity Leakage guarantee                         │
│  • Calibrated probabilities P(match | x) in [0.0, 1.0] │
└──────────────────────────┬─────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│ Threshold Optimization & Singletons (threshold.py)     │
│  • Grid search tau in [0.40, 0.95]                     │
```

## 2. Pairwise Feature Engineering (`src/matching/features.py`)

Each candidate pair $(S_1, S_{2/3})$ is converted into a 25-dimensional feature vector:

### Name Similarity Features
1. `name_exact_match`: Binary flag indicating if normalized business names are identical.
2. `name_core_match`: Binary flag indicating if business names match after stripping legal suffixes (`inc`, `llc`, `pvt ltd`, `sarl`, `corp`, etc.).
3. `name_token_jaccard`: Jaccard similarity of word token sets: $\frac{|A \cap B|}{|A \cup B|}$.
4. `name_token_dice`: Sorenson-Dice similarity of name tokens: $\frac{2 |A \cap B|}{|A| + |B|}$.
5. `name_token_sort_ratio`: SequenceMatcher similarity of alphabetically sorted name tokens.
6. `name_levenshtein_sim`: Normalized Levenshtein similarity: $1.0 - \frac{\text{LevDist}}{\max(\text{len}_1, \text{len}_2)}$.
7. `name_lcs_sim`: Longest Common Substring ratio: $\frac{2 \times \text{len}(\text{LCS})}{\text{len}_1 + \text{len}_2}$.
8. `name_ngram_jaccard`: Character 3-gram Jaccard similarity.
9. `name_len_diff_ratio`: Normalized string length discrepancy: $\frac{|\text{len}_1 - \text{len}_2|}{\max(\text{len}_1, \text{len}_2)}$.
10. `name_first_token_match`: Binary flag indicating if the leading business name word is identical.

### Address Similarity Features
11. `addr_exact_match`: Binary flag indicating exact address equality.
12. `addr_token_jaccard`: Jaccard token overlap between address strings.
13. `addr_token_dice`: Dice coefficient between address strings.
14. `addr_levenshtein_sim`: Normalized character Levenshtein similarity.
15. `addr_ngram_jaccard`: Character 3-gram Jaccard similarity.

### Numeric Token Agreement / Disagreement
16. `num_common_count`: Count of shared standalone numbers across address and name.
17. `num_jaccard`: Jaccard similarity of numeric tokens (house numbers, postal codes).
18. `num_disagreement`: **Strong negative indicator**. Binary flag equal to $1.0$ if both records contain numbers but their intersection is completely empty.

### Open-Set Country Comparison
19. `country_exact_match`: Binary flag ($1.0$ if both countries are non-empty and equal).
20. `country_mismatch`: Binary flag ($1.0$ if both countries are non-empty and differ).
21. `country_missing`: Binary flag ($1.0$ if either record lacks country metadata).
*Note: Never hardcoded to `{US, India}`; seamlessly generalizes to France and any unseen country.*

### Missingness Indicators
22. `name_missing_1`, 23. `name_missing_2`: Missing name indicators.
24. `addr_missing_1`, 25. `addr_missing_2`: Missing address indicators.

## 3. Supervised Model & Grouped Validation (`src/matching/train.py`)

### Grouped Validation (0% Leakage)
Splitting pairs at random causes massive data leakage because pairs belonging to the same reference $S_1$ entity would appear in both train and validation splits.
The module enforces strict **Grouped Splitting**:
- Group key: `source1_entity_id`.
- $\text{Train } S_1 \cap \text{Val } S_1 = \emptyset$.
- Ensures validation scores reflect generalization to completely unseen reference businesses.

### MatchingClassifier Architecture
- Standardized feature scaling (means and variances saved with model).
- Calibrated sigmoid probabilities: $P(\text{match} \mid x) = \frac{1}{1 + e^{-(w^T \tilde{x} + b)}}$.
- L2-regularized mini-batch optimization with class-imbalance weighting.
- Optional seamless acceleration via `scikit-learn` (`LogisticRegression` / `HistGradientBoostingClassifier`) when installed.
- Zero mandatory external C/Fortran binary dependencies; runs in standard Python environments.

## 4. Threshold Selection & Macro $F_{0.5}$ Evaluation (`src/matching/threshold.py`)

### Evaluation Metric
The challenge evaluates solutions using **Macro-averaged $F_{0.5}$** across all Source 1 entities:
$$\text{Macro } F_{0.5} = \frac{1}{|S_1|} \sum_{s \in S_1} F_{0.5}(s)$$
$$F_{0.5} = \frac{1.25 \times \text{Precision} \times \text{Recall}}{0.25 \times \text{Precision} + \text{Recall}}$$

### Singleton & NO-MATCH Invariants
- Singletons ($|T| = 0$):
  - Predict empty list $\implies F_{0.5} = 1.0$ (rewarded).
  - Predict any match $\implies F_{0.5} = 0.0$ (penalized false merge).
- Non-singletons ($|T| > 0$):
  - Predict empty list $\implies F_{0.5} = 0.0$ (missed match).
- Candidates are filtered: retain candidate $c$ for entity $s$ if and only if $P(\text{match} \mid s, c) \ge \tau$.
- Because $F_{0.5}$ weights precision $2\times$ over recall, optimal $\tau$ is high ($\approx 0.80 - 0.90$).

## 6. Execution Instructions

### Model Training & Grouped Validation
```bash
python3 src/matching/train.py \
    --data-dir dataset/sample \
    --candidates-path output/candidate_pairs.tsv \
    --model-out output/matching_model.json \
    --val-ratio 0.25 \
    --seed 42
```

### Match Prediction
```bash
python3 src/matching/predict.py \
    --model-path output/matching_model.json \
    --threshold 0.98 \
    --s1-path dataset/sample/train_source1.tsv \
    --s2-path dataset/sample/train_source2.tsv \
    --s3-path dataset/sample/train_source3.tsv \
    --candidates-path output/candidate_pairs.tsv \
    --output-path output/matching_results.tsv
```

```bash
python3 src/pipeline.py \

    --data-dir dataset/sample \
```

## 7. Upstream & Downstream Interface Contracts

1. **Input from Person 3 (Blocking):**
   - File: `output/candidate_pairs.tsv`
   - Format: `source1_entity_id \t candidate_entity_ids` (comma-separated, sorted, singletons with empty string).
   - In-memory contract: `candidate_pairs: Dict[str, List[str]]` or stream of candidate pair dictionaries.
2. **Reuse from Person 1 (Preprocessing):**
   - Module: `src.preprocessing.normalize`
   - Functions: `clean_business_name`, `clean_address`, `normalize_country`, `strip_legal_suffixes`, `extract_tokens`, `extract_numeric_tokens`.
3. **Output Contract:**
   - File: `output/matching_results.tsv`
   - Format: `source1_entity_id \t matched_entity_ids` (comma-separated, exactly one row per test S1 entity, empty string for singletons).
   - Validated against: `student_resource/utils/validate_submission.py` (Exit code 0 required).

## 8. Known Limitations & Future Improvements

1. **Non-Standard and Landmark-Based Indian Addresses:**
   - In Indian records, addresses often lack numeric house numbers or postal PIN codes and instead rely on descriptive landmarks (e.g., "Near SBI Bank, Bus Stand").
   - Pairwise address similarity for these records is lower, leading to higher false negative rates. Incorporating character n-gram cosine similarity or locality sub-word embeddings would enhance matching for landmark addresses.
2. **Open-Set Generalization (Unseen Countries like France):**
   - While features are completely language- and country-agnostic, training on US/India distributions may slightly underestimate token overlap in French names (accented characters like `é`, `è`, `ç`). Accented character folding during feature computation can further improve generalization.
3. **Chunked Streaming on Full 1.7M Test Set:**
   - The current streaming candidate reader processes candidate pairs in chunks of 50,000, ensuring low memory utilization (~150MB RSS) even on the full multi-gigabyte dataset.
